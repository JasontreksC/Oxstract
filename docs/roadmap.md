# 현황 점검과 수정 계획

작성일 2026-10-31. 기준 커밋 `c866728` (M1). 원래 범위는 [video-editor-plan.md](../video-editor-plan.md)이고, 이 문서는 그 뒤에 확정된 요구사항(여러 영상 순서 처리, 회전도 움직임으로 판정, 사설망 셀프호스팅)을 반영해 남은 일을 다시 묶는다. UI 개편은 [design/ui-redesign.md](design/ui-redesign.md)에 따로 있다.

## 1. 지금 상태 요약

검사 결과: `pytest` 22개 통과, `ruff`, `tsc`, `eslint`, `prettier`, `vite build` 모두 통과. 테스트는 스텁이 501을 낸다는 것까지만 확인하므로, 통과가 동작을 뜻하지 않는다.

"잘 작동하지 않는다"의 주된 이유는 버그보다 **핵심 파이프라인(M2~M6)이 아직 없다는 것**이다. 그 위에, 이미 있는 부분에도 아래 결함이 있다.

## 2. 이미 있는 코드의 결함

실행해서 확인한 것은 (확인)으로 표시했다.

### 2.1 객체 선택 화면이 실제로는 쓸 수 없다

- **영상 컨트롤이 막혀 있다.** `BoxSelectionOverlay`가 `.video-player__stage` 전체를 `position: absolute; inset: 0`으로 덮어서 `<video controls>`의 재생·탐색 버튼이 클릭되지 않는다. `frontend/src/index.css:135`.
- **재생 바와 영상이 따로 논다.** `VideoPlayer`의 range 입력은 React state만 바꾸고 `<video>`의 `currentTime`에 반영하지 않는다. 영상의 `timeupdate`도 state로 오지 않는다. 그래서 "이 장면에서 선택"이 화면에 보이는 프레임과 무관한 시각을 고른다. `frontend/src/components/VideoPlayer.tsx`.
- **박스 좌표가 영상 픽셀이 아니다.** 드래그 좌표가 오버레이(높이 360px 고정) 기준이고, `object-fit: contain`의 레터박스 여백도 빼지 않는다. 그대로 서버에 보내면 엉뚱한 영역을 추적한다. `frontend/src/types/selection.ts:1` 주석에 이미 적혀 있다.
- 탐지 박스는 `SAMPLE_DETECTIONS` 고정값이다. 민감도 입력은 `defaultValue`만 있는 비제어 입력이라 어디에도 전달되지 않는다. `frontend/src/App.tsx:17`, `:193`.
- 상단 탭으로 아무 때나 진행·타임라인 화면에 갈 수 있고, 거기엔 가짜 데이터(42%, 구간 2개, 길이 30초)가 나온다.

### 2.2 사설망 셀프호스팅에서 막히는 것

- **호스트 이름으로 접속하면 403.** Vite 6.4의 `server.allowedHosts` 검사 때문에 `http://oxstract.lan:5173` 같은 주소는 "Blocked request"가 뜬다. IP로만 열린다. (확인)
- **WebSocket이 서버에서 동작하지 않는다.** `backend/requirements.txt`가 `uvicorn[standard]`가 아닌 `uvicorn`이라 websockets 라이브러리가 없다. 실제 uvicorn은 업그레이드 요청에 404를 낸다. TestClient는 자체 구현이라 테스트에서는 드러나지 않는다. (확인)
- **Vite 프록시도 WebSocket을 넘기지 않는다.** `/jobs` 프록시에 `ws: true`가 없다. (확인)
- **Redis가 사설망 전체에 열려 있다.** `docker-compose.yml`의 `ports: "6379:6379"`는 0.0.0.0에 바인딩되고 비밀번호도 없다. 컨테이너 사이 통신에는 포트 공개가 필요 없다.
- **운영에서도 Vite 개발 서버를 띄운다.** `frontend/Dockerfile`이 `npm run dev`다. 빌드한 정적 파일을 백엔드가 같은 포트로 서빙하는 편이 단순하고, 포트 하나만 열면 된다.
- API 경로(`/videos`, `/jobs`)가 앞으로 넣을 화면 경로와 겹친다. `/api` 접두어로 옮겨야 프록시와 SPA 라우팅이 섞이지 않는다.

### 2.3 영상 처리 기초

- **휴대폰 영상(VFR, HEVC, 회전 메타데이터)에 약하다.** 길이를 `프레임 수 / fps`로 계산해서 가변 프레임레이트 영상에서 틀린다. 아이폰 HEVC `.mov`는 크롬·파이어폭스에서 재생이 안 될 수 있다. 업로드 직후 `ffprobe`로 정확한 메타데이터를 읽고, 미리보기·분석용 H.264 프록시를 만들어야 한다.
- 이미지에 FFmpeg가 없다. 컷·합성·프록시·한글 텍스트 카드 모두 FFmpeg와 Noto Sans CJK 글꼴이 필요하다.
- 업로드는 `fetch`라 진행률을 못 보여 준다. 대용량 파일 크기 제한, 디스크 여유 검사도 없다.
- 영상 목록·삭제 API가 없어서 새로고침하면 프론트가 올린 영상을 잃는다.

### 2.4 문서와 계획의 어긋남

- `video-editor-plan.md`는 영상 하나에 작업 하나를 가정한다. "여러 영상을 순서대로 처리해 하나로 출력"하려면 **프로젝트(여러 클립의 순서 목록)** 단위가 필요하다.
- 계획의 움직임 판정은 bbox 중심 이동량뿐이라 **제자리 회전을 잡지 못한다.**
- 계획 9장은 드라이브에 "API 키 + OAuth 클라이언트 ID"면 된다고 했지만, OAuth로 업로드할 때 API 키는 필요 없고 토큰 교환에 `client_secret`이 필요하다. 또 데스크톱 앱 OAuth는 서버의 `127.0.0.1`로 리디렉션되므로, 다른 PC의 브라우저에서는 승인을 끝낼 수 없다(5장 M7 참고).

## 3. 바뀐 설계

### 3.1 데이터 모델: 프로젝트와 클립

```text
Project  id, name, output_settings, created_at
  └─ Clip (순서 있음)  id, project_id, video_id, order,
        target {frame_t, bbox(원본 픽셀), source, class_name}
        analysis_status, analysis_progress
        options {move, rotate, min_len, gap_merge, padding}
        segments [{start, end, score, enabled, transition_after}]
Video   id, path, proxy_path, duration, fps, width, height, rotation, has_audio
Job     id, kind(analyze|render), ref_id, status, progress, stage, error, created_at
Render  id, project_id, path, drive_link, created_at
```

- 같은 영상을 두 클립에 넣을 수 있게 Video와 Clip을 나눈다.
- 결과 순서는 "클립 순서 → 클립 안 구간 시간순"이다. 전환은 결과 순서상 다음 컷과의 사이에 둔다. 클립 경계를 넘는 전환도 같은 방식이다.
- SQLite 그대로. 스키마 버전 표를 두고 시작할 때 마이그레이션한다.

### 3.2 작업 큐: Redis 대신 SQLite

사용자 한 명, GPU 한 장인 셀프호스팅이라 분산 큐가 필요 없다. 워커는 `jobs` 표에서 `queued`를 하나 집어(`UPDATE ... RETURNING`) 순서대로 처리하고 진행률을 같은 표에 쓴다. API는 그 값을 SSE(`GET /api/jobs/{id}/events`)로 흘린다. SSE는 일반 HTTP라 프록시 설정이 필요 없다.

- Redis 서비스와 `redis` 의존성을 뺀다. 구성 요소가 api, worker 둘로 준다.
- 워커가 시작할 때 `running`으로 남은 작업은 `failed`(재시도 가능)로 돌린다.
- 취소는 `cancel_requested` 플래그를 워커가 단계마다 확인한다.
- 백엔드와 워커가 같은 코드(`store`, `schemas`, `pipeline`)를 쓰도록 하나의 파이썬 패키지로 합치고 실행 명령만 나눈다.

### 3.3 분석과 구간 판정 분리 (핵심)

비싼 단계(디코딩, 추적, 움직임 신호 계산)와 싼 단계(임계값으로 구간 자르기)를 나눈다.

1. **분석** (워커, 클립당 한 번): 추적 결과와 프레임별 움직임 신호를 `signals.npz`로 저장한다.
2. **구간 판정** (API, 즉시): 저장된 신호에 임계값, 히스테리시스, 병합, 최소 길이, 여유를 적용한다. 수 밀리초면 끝난다.

그래서 화면에서 민감도 슬라이더를 움직이면 다시 추적하지 않고 타임라인이 바로 바뀐다. 사용자가 손으로 고친 구간은 `manual` 표시를 남겨 재판정 때 덮어쓰지 않는다.

### 3.4 추적

- 분석은 원본이 아니라 프록시(짧은 변 480~640px, 10~15fps)로 한다. 움직임 판정에는 이 정도 해상도와 시간 간격이면 충분하고 속도가 몇 배 빨라진다. 구간 경계는 원본 PTS로 환산한다.
- 고른 프레임에서 앞뒤 양방향으로 추적한다(앞으로 한 번, 뒤집어서 한 번).
- `Tracker` 인터페이스 아래 구현을 둔다.
  - **기본(CPU 가능)**: 탐지 박스로 골랐으면 YOLO11 + BoT-SORT로 매 샘플 프레임을 탐지하고, 고른 박스와 IoU가 가장 큰 트랙을 따라간다. 트랙이 끊기면 마지막 위치 근처 같은 클래스 박스로 다시 잇는다. 드래그로 골랐으면 OpenCV `TrackerVit`(없으면 CSRT)로 추적하고, 일정 간격으로 신뢰도를 검사해 놓치면 "사라짐"으로 표시한다.
  - **고급(GPU, 선택)**: SAM 2.1 비디오 예측기에 박스 프롬프트를 주고 마스크로 추적한다. 회전·변형에 가장 강하지만 GPU가 필요하다. 지금 서버에서는 쓰지 않는다.
- **서버는 CPU 전용으로 정한다** (2026-10-31 확인: 그래픽카드가 오래되어 가속을 쓸 수 없고, 오래 걸려도 결과만 나오면 된다). 그래서 기본값은 YOLO11n(CPU, PyTorch CPU 휠 또는 ONNX Runtime), OpenCV 추적기, 짧은 변 480px·10fps 프록시 분석, libx264 소프트웨어 인코딩이다. CUDA 이미지와 NVENC는 쓰지 않는다.
- 분석이 수 분에서 수십 분 걸릴 수 있으므로 진행률, 남은 시간 추정, 취소, 재시작 후 이어하기(구간 신호를 청크 단위로 저장)를 처음부터 넣는다.

### 3.5 움직임 신호: 이동 + 회전

샘플 프레임 쌍마다 아래를 계산해 저장한다.

| 신호 | 계산 | 잡는 것 |
|---|---|---|
| 이동 | 중심점 이동량 ÷ bbox 대각선 | 화면 안 위치 이동 |
| 크기 변화 | `abs(log(면적비))` | 다가오거나 멀어짐 |
| 평면 회전 | bbox(또는 마스크) 안 특징점을 LK로 추적 → `estimateAffinePartial2D`의 회전각, 초당 도로 환산 | 제자리 회전 |
| 내부 움직임 | bbox 안 Farneback 광학 흐름 크기의 75백분위 ÷ 대각선 | 입체 회전, 표면이 돌아가는 움직임 |
| 카메라 보정 | bbox 바깥 테두리 영역 흐름의 중앙값을 위 값들에서 뺀다 | 손떨림, 카메라 패닝 |
| 가시성 | 추적 신뢰도. 놓치면 0 | 화면 밖 구간 제외 |

판정: `이동 > T_move` 또는 `회전 > T_rot` 또는 `내부 > T_flow`이면 움직임. 이동 평균으로 다듬고 들어가는 값과 나오는 값이 다른 히스테리시스를 둔다. 이어서 짧은 정지 병합, 최소 길이 미만 제거, 앞뒤 여유를 적용한다. 각 구간 `score`는 구간 안 신호 평균을 0~1로 정규화한 값이다.

UI에는 이 신호를 그래프로 보여 주고 임계선을 끌어 조정하게 한다.

### 3.6 렌더

복잡한 `xfade` 필터 그래프 대신 중간 클립을 만들고 이어 붙인다.

1. 출력 규격을 정한다: 해상도(첫 클립 기준 또는 1080p/720p 선택), fps, H.264 `yuv420p`, AAC 48kHz 스테레오. 규격이 다른 클립은 스케일과 패딩으로 맞춘다. 오디오 없는 클립은 `anullsrc`로 무음 트랙을 넣는다.
2. 구간마다 정확한 컷으로 재인코딩한다. 계획 5.5의 페이드(앞 컷 페이드 아웃, 다음 컷 페이드 인)는 이 단계에서 `fade`/`afade` 필터로 클립 끝과 처음에 바로 넣는다.
3. 텍스트 카드는 `color` 소스 + `drawtext`(Noto Sans CJK, 줄바꿈과 가운데 정렬)로 같은 규격의 클립을 만든다.
4. 모든 중간 클립이 같은 규격이므로 concat demuxer로 이어 붙인다. 경계에서 오디오가 튀면 오디오만 concat 필터로 다시 인코딩한다.
5. `-progress pipe:1`의 `out_time`으로 진행률을 낸다. `-movflags +faststart`. 인코딩은 libx264 소프트웨어(CPU 서버).
6. 결과 옆에 원본 시각 기준 구간 JSON을 저장한다. 임시 파일은 성공·실패 모두 지운다.

교차 페이드(`xfade`)는 이후 전환 종류를 늘릴 때 추가한다.

## 4. 마일스톤

각 단계 끝에 그 단계만으로 화면에서 확인할 수 있게 나눴다. 기존 계획의 M2~M7을 대체한다.

### M1.5 기반 정리 (짧게, 먼저) — 끝남 (2026-10-31)

아래를 모두 넣었다. 남은 확인: Docker 이미지 빌드는 개발 기계에 Docker 권한이 없어 아직 직접 돌려 보지 못했다.

- API를 `/api`로 옮기고 `uvicorn[standard]` 사용. 백엔드가 빌드된 프론트를 같은 포트로 서빙.
- 백엔드·워커 단일 패키지화, Docker 이미지에 FFmpeg와 `fonts-noto-cjk` 추가.
- Redis 제거, SQLite 작업 표와 워커 폴링 루프, SSE 진행률.
- `docker-compose.yml`: Redis 포트 공개 제거, 개발용 `allowedHosts` 또는 `.env`의 `APP_HOSTNAME` 반영.
- 업로드 후 `ffprobe` 메타데이터와 프록시 생성을 첫 작업 종류로 넣는다(큐가 실제로 도는지 확인하는 용도도 겸함).
- `GET/DELETE /api/videos`, 프로젝트·클립 CRUD와 순서 변경.
- 완료 기준: 여러 영상을 올리면 프록시가 만들어지고, 새로고침해도 프로젝트와 클립 목록이 남는다.

### M2 대상 지정과 탐지 — 끝남 (2026-10-31)

### M6 성능 — 끝남 (2026-10-31)

`scripts/benchmark.py`가 이제 추정이 아니라 실제로 잰다. 영상을 주거나, 없으면 합성 영상(원판이 멈춤·이동·회전·화면 밖·복귀, 카메라 패닝, 소리)을 만들어 미리보기 → 분석 → 렌더를 앱 코드 그대로 돌리고, 단계마다 새 프로세스에서 시간과 최대 메모리(FFmpeg 포함)를 적는다.

```bash
python scripts/benchmark.py --class "sports ball" --work ~/.cache/oxstract-bench
```

이 서버(Pentium G4400 2코어, 메모리 7GB, GPU 없음)에서 10분 1080p30 합성 영상:

| 단계 | 시간 | 영상 대비 | 최대 메모리 |
|---|---|---|---|
| 미리보기(720p) | 122초 | 0.20배 | 300 MB |
| 분석, 직접 그린 대상 | 138초 | 0.23배 | 160 MB |
| 분석, 탐지 대상 | 279초 | 0.47배 | 282 MB |
| 렌더 1080p 보통(결과 225초) | 327초 | 0.54배 | 627 MB |

품질별 렌더(같은 225~236초 결과): 1080p 보통 결과 길이의 1.2~1.45배, 1080p 작게 0.46배, 720p 보통 0.57배. 기본값은 바꾸지 않았다.

분석이 빨라진 이유(1분 구간 프로파일 기준, 직접 그린 대상 32.6초 → 13.4초, 탐지 대상 50.3초 → 33.8초):

- CSRT는 특징점이 박스를 못 정할 때만 돈다. 특징점이 있으면 그 결과를 쓰므로 CSRT 갱신은 버려지던 계산이었다(전체의 42%).
- 샘플마다 박스의 SIFT 특징을 한 번만 구한다(기준 모습과 최근 모습에 각각 구하던 것). 전체 화면 검색도 프레임 특징을 한 번만 구한다.
- 박스 안 특징점 찾기는 박스 영역만 본다(전체 화면에 마스크를 씌우던 것).
- 탐지 대상의 YOLO 확인은 추적 중 2초마다, 놓친 동안 1초마다(특징점·색 검색은 0.3초마다).

추적 정확도도 고쳤다(실제 Test1 프로젝트의 두 클립과 합성 영상 정답으로 확인):

- 화면 끝에서 잘린 박스로 "최근 모습"을 갱신하던 것을 막았다. 대상이 돌아오면 그 좁은 모습으로 찾아 박스가 반쪽으로 남았다(합성 영상 크기 오차 105px → 7px 이내).
- 무늬 점수: 상대 쪽 특징점은 한 번씩만 세고(여러 개가 한 점에 짝지어져 빈 바닥이 0.98점을 받았다), 두 쪽 중 적은 쪽에 대한 비율로 센다(작게 보인 대상도 공정하게).
- 계속 따라가기와 다시 찾기의 기준을 나눴다. 따라가는 중에는 박스에 특징점이 있고 색이 맞으면 대상이 있는 것으로 본다(작게, 돌아가 보이는 로봇을 놓치지 않게). 빈 바닥·벽처럼 특징점이 없거나 색이 다르면 놓친 것이다. 다시 찾기는 여전히 닮음 0.65 이상이어야 한다.
- 다시 찾기에 색 검색(기준 색 분포를 화면에 투영)을 더했다. 화면 가장자리에 걸친 후보는 다 들어온 뒤에 잡는다. 박스가 대상에 반쯤 걸친 애매한 상태면 0.3초마다 더 닮은 곳을 찾아 옮긴다.

남은 것: 이 서버에서 GPU 없이 SAM 2.1이나 NVENC는 쓰지 않는다. GPU 서버로 옮길 일이 생기면 그때 선택 옵션으로 추가한다.
